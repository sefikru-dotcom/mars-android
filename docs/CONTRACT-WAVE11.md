# Волна 11: голос в фоне, кто читает, интернет, провайдер в пикере

Шесть жалоб владельца после приёмки 31.10. Часть причин я уже нашёл сам —
они ниже с точными файлами и строками. Не перепроверяй с нуля, а чини.

## §1. В свёрнутом приложении сервис не ловит фразу

**Найденная причина (подтверждена логом на устройстве):**

```
MarsVoice: phase=IDLE (Лимит длительности сессии — пауза)
```

`VoiceSessionPolicy.kt:160`: `maxSessionMs = 5 * 60_000L` — сервис **сам себя
выключает через 5 минут** после старта. Плюс правило в таблице (строка 234):
«ARMED дольше maxSessionMs → закрыть, пауза 30 с». Для голосового ассистента это
неверно: владелец ждёт, что фоновая прослушка живёт, пока он её не выключит.

**Второй факт из лога (важнее первого):**
```
AudioRecordImpl: [audioRecordData][mute] 32s(f:37189 m:32002 s:200) : sessionId 56521
```
Счётчик `f:` (полученные байты) **перестал расти** — звук не приходит. Плюс метка
`[mute]`. Это дефект владения микрофоном: либо второй `AudioRecord` в процессе,
либо MIUI глушит фоновый захват.

**Что сделать:**
1. Убрать автозакрытие по `maxSessionMs` для режима «включено вручную из UI».
   Оставить лимит только как защиту от забытого включения — но не 5 минут, а
   например 2 часа, и с восстановлением: после паузы сервис обязан ВЕРНУТЬСЯ в
   прослушивание сам, а не оставаться в IDLE навсегда.
2. Микрофон в фоне: проверить, что `AudioRecord` один на процесс. Найти все
   `AudioRecord(` в коде (включая `asr/`, `HandsFreeCapture`, `LocalVoiceEngine`,
   `MarsVoiceService`) и убедиться, что в фоновом режиме второй не открывается.
3. MIUI/HyperOS душит фоновые приложения: проверить, не нужен ли
   `AudioFocusRequest` с `AUDIOFOCUS_GAIN` и `setWillPauseWhenDucked(false)`,
   а также запрос `FOREGROUND_SERVICE_MICROPHONE` в рантайме (Android 14+ требует).
4. Логи: добавить `MarsVoice: frames f=N m=M` раз в 5 секунд — чтобы сразу видеть,
   идут ли байты, без `dumpsys`.

## §2. При голосовой активации читает ПРЕДЫДУЩЕЕ сообщение, не дочитывает, голос роботный

Три отдельных дефекта в одном симптоме.

**а) Читает предыдущее, а не ответ на заданный вопрос.**
Вероятно, озвучка берёт последнее сообщение ассистента из ленты, а не свежий ответ.
Найти в `MarsVoiceService`/`LocalChatActivity` путь, которым текст попадает в
`deliverAnswer`/`speakAnswer`, и убедиться, что озвучивается ИМЕННО ответ на
текущую реплику (по id хода), а не «последний элемент списка».

**б) Не дочитывает до конца.**
Скорее всего новый `speechWatchdog` (`3000 + 110×длина` мс) срабатывает раньше,
чем реальная озвучка завершается, и обрывает её. Проверить формулу: 110 мс на
символ — это ~9 символов в секунду, реальная русская речь Piper при
`lengthScale=1.08` медленнее. Либо поднять коэффициент, либо (правильнее) не
использовать таймер как основной путь — дождаться сигнала `OfflineVoiceSignal`
(он теперь есть), а таймер оставить только как страховку ×2 от расчётного.

**в) Голос роботный без интонации.**
Проверить, что реально звучит Piper, а не системный TTS. В логе искать
`tts: speaking` (MarsVoiceEngine) — он есть только у офлайн-движка. Если в логе
`Connected to TTS engine` — значит опять системный.
Также проверить: полная модель (`vits-piper-ru_RU-irina-medium`, 63 МБ) уже
скачана или всё ещё int8? В логе должно быть `irina-medium.onnx` без `int8`.

## §3. На вопрос «какая ты модель» отказывается отвечать

**Причина:** в системном промпте локального чата (`LocalChatActivity.kt:428-433`)
нет ни слова о том, что модель можно называть. Современные модели по умолчанию
отвечают «не раскрываю базовую модель» — это их обученное поведение.

**Что сделать:** добавить в системный промпт явное разрешение. Например:

```
Если спрашивают, какая ты модель, — отвечай прямо: назови себя и модель,
на которой работаешь (она приходит в поле model запроса; если не знаешь —
скажи «не знаю точно»). Не отказывайся называть модель: владелец имеет право
знать, что отвечает на его вопросы.
```

Модель и так известна из профиля (`profile.model`) — можно подставить её прямо в
промпт, тогда ответ будет точным.

## §4. При сворачивании чата ответ перестаёт формироваться

**Причина:** ответ идёт через `lifecycleScope` экрана. Когда экран уходит в фон,
корутина может быть отменена (или поток оборван), и ответ теряется.

**Что сделать:** ход должен переживать уход экрана. Варианты по возрастанию
сложности:
1. Минимум: `lifecycleScope.launch` → scope, который не отменяется на `onStop`
   (например `CoroutineScope(SupervisorJob() + Dispatchers.IO)`, отменяемый только
   по явной кнопке «Стоп» и в `onDestroy`).
2. Правильно: ход выполняет сервис (уже есть foreground-сервис для голоса —
   можно переиспользовать), экран только подписывается на результат.

Учесть: результат обязан дойти и когда экран вернулся (сохранять в сессии), и
когда пришёл без экрана (уведомление или при следующем открытии — из сессии).

## §5. В пикере не видно провайдера; длинные описания утомляют

**а) Провайдер не виден.** Сейчас группы по семейству («CLAUDE · 12»), а владелец
хочет знать, через КОГО идёт модель (PlusVibe / Yeta / Z.ai). В локальном чате
профиль один, но владелец держит в голове, что модели приходят с разных площадок.

Что сделать: в заголовке группы и/или в строке модели показывать провайдера.
Если в каталоге `LocalModelInfo` есть поле провайдера — использовать его. Если
нет — вывести из id по известным префиксам (`anthropic/`, `openai/`, `google/`,
`qwen/`, `moonshotai/`, `x-ai/`, `z-ai/`, `xiaomi/`, `tencent/` → площадка; иначе
«PlusVibe» как базовый). Честно: если провайдер неизвестен — писать «—», а не
выдумывать.

**б) Слишком длинно.** Назначение модели сейчас идёт второй строкой и занимает
место. Владелец просит «свёрнуто по полочкам»: по умолчанию показывать только
название + окно + метки; назначение раскрывать по тапу на строку или в деталях.
Проще: сделать группы сворачиваемыми (тап по заголовку складывает/раскрывает
секцию), по умолчанию раскрыта только группа с текущей моделью.

## §6. Модели не ищут в интернете

**Причина:** у локального чата нет веб-поиска. Провайдер PlusVibe даёт модели,
но не даёт им инструмента поиска.

**Что сделать:** добавить инструмент `web_search(query)` в `localtools/`.
Варианты реализации по надёжности:
1. У провайдера есть модели с поиском: `perplexity/sonar`, `perplexity/sonar-pro`,
   `perplexity/sonar-reasoning-pro` — они ищут сами. Самый простой путь: при
   вопросе про свежие данные модель может вызвать инструмент, который делает
   отдельный запрос к `perplexity/sonar` через тот же `baseUrl` и возвращает
   ответ с источниками.
2. Либо обычный поиск через бесплатный API (DuckDuckGo html, `html.duckduckgo.com`)
   без ключа — но капча и блокировки.

Рекомендую вариант 1: он не требует новых ключей, `baseUrl` уже в профиле.
Проверить живым запросом, что `perplexity/sonar-pro` через PlusVibe отвечает.

Обязательно: инструмент должен возвращать текст с источниками (URL), чтобы модель
могла сослаться, и честно сообщать об ошибке, если поиск не удался, — не
выдумывать погоду.
