# Волна 10: модель не переключается, пикер, контекст, фоновый голос

Пять жалоб владельца. Три из них — про локальный чат, одна про серверный, одна про голос.

## §1. Смена модели не действует (ГЛАВНОЕ)

Симптом: выбираешь любую модель в пикере — отвечает всегда `claude-haiku-5.5`.

**Что уже проверено мной на сервере (не гадать):** провайдер PlusVibe принимает
ВСЕ модели и возвращает в ответе ровно тот `model`, который попросили:
- `gpt-6.1-sol` → `"model":"gpt-6.1-sol"` ✅
- `google/gemini-3.8-flash` → `"model":"google/gemini-3.8-flash"` ✅

То есть провайдер не виноват. Проблема в приложении.

**Что проверено в коде и выглядит верно:**
- `LocalProviderPrefsStore.saveProfile` пишет `model` в JSON и читает обратно;
- `LocalChatPresenter.send` берёт `profile.model` в `activeProfile`;
- `OkHttpLocalChatClient` подставляет `profile.model` в тело запроса без подмены;
- `applyModel` в `LocalChatActivity` зовёт `saveProfile` + `presenter.setModel`.

Значит расхождение где-то в цепочке «выбор в пикере → следующий запрос».
Вероятные места (проверить каждое):
1. `applyModel` вызывается, но следующий `send` берёт профиль из ДРУГОГО источника
   (например, из `providerStore.state().active` до сохранения, или из локальной копии).
2. `LocalProviderState.activeId` указывает на другой профиль, чем тот, что правят.
3. `onProfileChange` презентера возвращает профиль, перезаписывая `model` старым.
4. Пикер отдаёт `info`, но `catalog[info.id] = info` и `saveProfile` идут по профилю
   с ДРУГИМ `id` (если пикер открыт для профиля A, а active — B).
5. Для серверного чата модель уходит в WebUI другим полем (не `model`), и сервер
   игнорирует выбор.

**Требование:** после смены модели СЛЕДУЮЩИЙ запрос обязан содержать её. Проверять
не глазами, а логом: добавить в клиент одну строку лога вида
`Log.d("MarsModel", "request model=${profile.model}")` и в отчёте показать строки
до и после смены. Без этого доказательства задача не закрыта.

## §2. Пикер моделей: сортировка по провайдерам, бедный вид

Симптом: список плоский, провайдеры не разделены, выглядит бедно.

**Проверить, что каталог названий реально подключён.** В прошлой волне
`LocalModelHints`/`LocalModelPickerPolicy` были написаны, но R8 их вырезал —
их никто не звал. Я подключил, но проверь: в `mapping.txt` должно быть
`LocalModelHints` > 0 упоминаний.

**Что сделать:**
1. Разделители-заголовки групп по провайдеру: «PlusVibe», «Yeta», «Z.ai» —
   липкие заголовки либо просто жирная строка между группами.
2. Показывать для каждой модели: человеческое название, назначение, окно
   контекста, метку vision. Не только id.
3. Второй профиль провайдера (если воркер прошлой волны его сделал — подключить,
   если нет — сделать): в конфиге сервера у владельца четыре провайдера, и он

   не «простыня строк».

## §3. Процент контекста непонятен — нужна полоса как в серверном чате

Симптом: в локальном чате показывает «3.1k / 1M · 0%», непонятно и некрасиво.
В серверном чате Марса есть полоса заполнения — владелец хочет так же.

**Что сделать:** в локальном чате нарисовать полосу контекста в том же стиле,
что на сервере (найти в коде серверного чата `ChatParamRowPresenter` /
`ComposerLayoutPresenter`, узел `CONTEXT`, и повторить вид: тонкая полоса
заполнения + подпись). Обязательно:
- цвет меняется по порогам (`LocalContextPolicy` уже считает 50/75 — использовать);
- на узком экране (POCO F5) не растягивает строку, `min-width: 0` у контейнера;
- процент и токены читаемы без наведения.

## §4. Фоновый голос так и не работает

Симптом: «фоновый голосовой вызов так и не начал работать корректно».

**Известное состояние (не перепроверять с нуля, это факты с устройства):**
- сервис стартует: `Background started FGS: Allowed`, `KeywordSpotterConfig` с
  моделями, `AudioRecord: start sr 16000 ch 1`, уведомление `mars_voice_conversation`;
- кнопка в чате и сервис НЕ делят микрофон: введён `conversationActive`;
- фазовой ловушки `THINKING` больше нет;
- wake word нельзя проверить программно — нет `cmd text-to-speech` на POCO.

**Что чинить (проверить по коду и логам):**
1. После ответа сервис обязан ВЕРНУТЬСЯ в режим «слушаю фразу», а не остаться в
   `THINKING`/`IDLE`. Найти в `MarsVoiceService` путь после `deliverAnswer` и
   убедиться, что детектор поднимается заново.
2. Микрофон не должен закрываться до ответа: если `AudioRecord` освобождается
   сразу после распознавания реплики, второй раз фраза не поймается.
3. Экранный `onPause` не должен глушить сервис: сейчас в `LocalChatActivity`
   `onPause` зовёт `voice.onPause()` — проверить, не убивает ли это фоновый тракт.
4. Логи: добавить в сервис явные строки жизненного цикла —
   `"voice: phase=WAKE"`, `"voice: heard phrase"`, `"voice: speaking"`,
   `"voice: back to WAKE"`. Без них следующий разбор опять будет наугад.

**Требование к отчёту:** показать последовательность этих строк из реального
прогона на устройстве, если телефон подключён; если нет — честно сказать, что
не проверено, и показать, где именно в коде теперь происходит возврат в WAKE.
